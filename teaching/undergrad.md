# Teaching: undergraduate level

## How to use this at this level

An undergraduate does not need to design a research pipeline. The goal is to take a research question, find the template in the skills directory that matches it, and fill that template in without changing its logic. The templates are the product; your job is to use one correctly. Copy the one that fits, replace the placeholders with your own question, sample, and data, and run it end to end. The test of whether you are done is the template's own acceptance list, not whether the output looks impressive.

At this level identification is a concept, not a task. You need to understand that every empirical claim rests on a comparison, that the comparison has a treatment group and a control group, and that the paper must say which is which. You do not need to defend a design against a referee, build an instrument, or test parallel trends for your own paper. You need to read the identification section of a published paper and say in one sentence what is being compared with what, and why anyone believes the comparison is fair.

The skill this level should practice most is stating the need precisely. Before touching data, write down five things: the question in one sentence, the unit of observation, the outcome variable and its exact definition, the comparison the answer will rest on, and what file you will hand in. A request that contains all five can be executed by a template. A request that contains none of them cannot be executed by anything, no matter how advanced the tooling.

## Which skills to use

| Skill | When to use | What to watch at this level |
| feasibility | Before choosing a topic, to check whether a usable dataset and a comparison exist | You are checking that data and a comparison exist, not proving that a design is credible |
| identification | When reading a paper, or when asked to name the comparison in your own question | Learn the vocabulary and the idea of treatment and control; do not attempt to invent a design |
| data-prep | After the template is chosen, to put your data into the shape the template expects | Follow the template's variable definitions literally; write down every change you made to the raw data |
| estimation | To run the regression the template specifies | Run the baseline first; do not add controls the template does not list |
| tables-figures | To turn output into the table and figure the template requires | Use the template's table layout and include the notes it asks for |
| report | To assemble the folder that reruns your work from raw data | The test is that a classmate can rerun it, not that the folder is tidy |
| writing | To describe what you did and what the results show | Describe, do not argue for a contribution; report estimates with their uncertainty |
| review | Only if you are in a reading group or commenting on a classmate's draft | Comment on clarity and definitions, not on whether the design would publish |

## What not to do

1. Do not invent an identification strategy of your own. A design you cannot defend loses more marks than a template design executed correctly; if the template does not fit your question, change the question, not the design.
2. Do not treat the regression output as the result before running the template's acceptance list. The output is evidence for the template; the acceptance list is what makes it a deliverable.
3. Do not change the template's sample or variable definitions silently. Every restriction you alter changes the comparison, so record it and be able to say why.
4. Do not put a number in the text that you did not compute. If a statistic is missing, write a placeholder and keep going; a plausible-looking number that is not in your output is the one mistake that cannot be fixed later.
5. Do not report only the specification that produced the expected sign. Report the specifications you ran, including the ones that did not work, and say what they showed.
